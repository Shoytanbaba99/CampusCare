\begin{abstract}
\noindent
CampusCare is an internal, web-based 3-tier ticketing and facility helpdesk application designed specifically for university campus infrastructure management. In many higher education institutions, maintenance reporting relies on unorganized communication channels such as verbal walk-ins, phone calls, and unmonitored emails. This fragmentation leads to misplaced requests, delayed issue resolutions, zero progress visibility for reporters, and a complete lack of administrative oversight regarding institutional asset health. 

CampusCare addresses these operational challenges by implementing a centralized digital pipeline governed by a strict state machine workflow (\texttt{Submitted} $\rightarrow$ \texttt{Assigned} $\rightarrow$ \texttt{In Progress} $\rightarrow$ \texttt{Resolved} $\rightarrow$ \texttt{Closed} / \texttt{Reopened}). Built using modern full-stack web technologies—including Next.js (App Router, React 19, TypeScript), Tailwind CSS, Shadcn UI, and Supabase (PostgreSQL engine with Row Level Security policies and Supabase Storage)—the platform provides isolated, role-based interfaces for Students (End-Users), Staff (Resolvers), and Administrators (Dispatchers \& Analysts).

This Software Requirements Specification (SRS) document presents a comprehensive analysis of CampusCare, detailing the functional requirements, non-functional performance benchmarks, relational database entity schemas, behavioral system models (Use Case, Class, State Machine, ER, Sequence, and Data Flow Diagrams), and a traceably mapped system testing plan.
\end{abstract}

\section{Overall Description}

\subsection{Product Perspective}
CampusCare is a standalone, web-based application built using a 3-tier architecture:
\begin{itemize}[leftmargin=*]
    \item \textbf{Presentation Tier:} Next.js (App Router, React 19, TypeScript) rendered with Tailwind CSS and Shadcn UI components.
    \item \textbf{Application Tier:} Server-side business logic, API endpoints, and Next.js Server Actions enforcing Zod input validation schemas.
    \item \textbf{Data Tier:} PostgreSQL database hosted via Supabase enforcing engine-level Row Level Security policies and Supabase Storage buckets for photographic attachments.
\end{itemize}

\subsection{Product Functions}
The principal functions of CampusCare are summarized below:
\begin{itemize}[leftmargin=*]
    \item User Authentication \& Session Management via \texttt{HttpOnly} cookies.
    \item Categorized Complaint Lodging with optional photo evidence attachment.
    \item Unique Complaint ID auto-generation (\texttt{CMP-YYYY-XXXX}).
    \item Departmental Ticket Queue Routing \& SLA Deadline Calculation.
    \item Interactive Status Progression (\texttt{Submitted} $\rightarrow$ \texttt{Assigned} $\rightarrow$ \texttt{In Progress} $\rightarrow$ \texttt{Resolved} $\rightarrow$ \texttt{Closed} / \texttt{Reopened}).
    \item Resolution Verification Feedback Loop (Student Confirmation \& Optional Anonymous 1--5 Star Rating).
    \item Administrative Master Data Dispatching, Priority Override, and Taxonomy Configuration.
    \item Immutable PostgreSQL Database Trigger Audit Logging.
\end{itemize}

\subsection{Operating Environment}
\begin{itemize}[leftmargin=*]
    \item \textbf{Client Side:} Modern desktop and mobile web browsers (Chrome, Safari, Firefox, Edge) with JavaScript enabled. Minimum viewport width: 320px.
    \item \textbf{Server Side:} Node.js 20+ execution environment hosting Next.js.
    \item \textbf{Database Engine:} PostgreSQL 15+ hosted via Supabase Cloud.
\end{itemize}

\subsection{Design and Implementation Constraints}
\begin{itemize}[leftmargin=*]
    \item \textbf{Security Constraint:} Authentication tokens must never be exposed to client JavaScript or stored in \texttt{LocalStorage}. Tokens are stored strictly in \texttt{HttpOnly}, \texttt{SameSite=Lax}, \texttt{Secure} cookies.
    \item \textbf{Data Isolation Constraint:} PostgreSQL Row Level Security (RLS) policies must be enabled on 100\% of database tables to prevent unauthorized cross-tenant data access.
    \item \textbf{File Upload Constraint:} Image attachments are strictly limited to JPEG, PNG, and WEBP formats with a maximum file size of 5MB per upload.
\end{itemize}

\subsection{User Documentation}
User documentation will include online dashboard tooltips, inline form field guides, and a digital PDF User Manual for Staff Resolvers and Administrators.

\subsection{Assumptions and Dependencies}
\begin{itemize}[leftmargin=*]
    \item \textbf{University Email Integration:} The system assumes students and staff register and log in using their official university email addresses.
    \item \textbf{Cloud Service Availability:} Supabase Cloud infrastructure (PostgreSQL database, Storage buckets, and Authentication endpoints) maintains an operational availability exceeding 99.5\% uptime.
    \item \textbf{Network Infrastructure:} Campus Wi-Fi and mobile networks are available across university premises.
\end{itemize}

The application exposes three responsive user interface views:

\subsection{Communications Interfaces}
The platform enforces encrypted Transport Layer Security (TLS 1.3) across all client-server communications via HTTPS. API payloads observe standard JSON format over HTTP POST/GET requests.

\section{System Features (Functional Subsystems)}

\subsection{Student Module: Complaint Submission \& Tracking Engine}

\subsubsection{Description and Priority}
This subsystem allows authenticated students to lodge facility complaints with detailed location descriptions and optional photo attachments, track status changes in real-time, and view progress notes. Priority: \textbf{High}.

\subsubsection{Stimulus / Response Sequences}
\begin{itemize}[leftmargin=*]
    \item \textbf{Stimulus:} Student clicks "Submit Complaint" and fills out form fields.
    \item \textbf{Response:} System validates payload via Zod, uploads optional evidence to storage, generates a unique \texttt{CMP-YYYY-XXXX} ID, inserts database record, and displays success receipt.
    \item \textbf{Stimulus:} Student selects a ticket from their dashboard list.
    \item \textbf{Response:} System fetches ticket record and renders a chronological tracking timeline with progress notes and assigned staff details.
\end{itemize}

\subsubsection{Functional Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 4.1.A - Session Authentication:} The system shall restrict student portal access to authenticated users possessing the \texttt{student} role.
    \item \textbf{Requirement 4.1.B - Complaint Form Fields:} The system shall require title, category selection, location details, priority level, and detailed description during submission.
    \item \textbf{Requirement 4.1.C - Photo Upload Validation (Optional):} The system shall support optional image attachments, validating files for type (JPG, PNG, WEBP) and maximum size (5MB).
    \item \textbf{Requirement 4.1.D - Ticket Number Generation:} The system shall automatically execute a database trigger function generating a human-readable Complaint ID (e.g., \texttt{CMP-2026-0001}).
    \item \textbf{Requirement 4.1.E - Personal Data Isolation:} The system shall prevent students from viewing or searching complaints lodged by other students via PostgreSQL RLS policies.
    \item \textbf{Requirement 4.1.F - Real-Time Timeline Rendering:} The system shall render a chronological timeline displaying ticket creation, staff assignment, progress updates, and resolution status.
\end{itemize}

\subsection{Staff Module: Task Queue \& SLA Resolution Workflow}

\subsubsection{Description and Priority}
This subsystem provides maintenance and technical staff with a queue of tickets assigned to their department, SLA warning indicators, progress note submission forms, repair proof uploads, and status transition toggles. Priority: \textbf{High}.

\subsubsection{Stimulus / Response Sequences}
\begin{itemize}[leftmargin=*]
    \item \textbf{Stimulus:} Staff member logs in and opens the departmental dashboard.
    \item \textbf{Response:} System queries database for complaints matching the staff member's department ID and renders a prioritized queue with SLA badges.
    \item \textbf{Stimulus:} Staff member clicks "Accept Ticket".
    \item \textbf{Response:} System updates ticket status from \texttt{Assigned} to \texttt{In Progress} and records an audit log entry.
    \item \textbf{Stimulus:} Staff member appends a note and uploads a repair photo, then clicks "Mark Resolved".
    \item \textbf{Response:} System updates ticket status to \texttt{Resolved}, attaches repair proof, and notifies the reporting student.
\end{itemize}

\subsubsection{Functional Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 4.2.A - Department Queue Filtering:} The system shall restrict staff queue views strictly to tickets matching their assigned operational department.
    \item \textbf{Requirement 4.2.B - SLA Target Display:} The system shall display visual warning indicators for tickets approaching or exceeding target SLA resolution deadlines.
    \item \textbf{Requirement 4.2.C - State Transition to In Progress:} The system shall allow staff members to accept assigned tickets, transitioning state to \texttt{In Progress}.
    \item \textbf{Requirement 4.2.D - Progress Note Logging:} The system shall allow staff to append public or internal chronological notes to active tickets.
    \item \textbf{Requirement 4.2.E - Repair Proof Upload \& Resolution:} The system shall support photographic repair completion uploads and allow staff to mark tickets as \texttt{Resolved}.
\end{itemize}

\subsection{Admin Module: Dispatcher Command Center \& Audit Ledger}

\subsubsection{Description and Priority}
This subsystem provides facility managers with global ticket routing, staff re-assignment, priority escalation, user management, category administration, analytics charts, and immutable audit logs. Priority: \textbf{High}.

\subsubsection{Stimulus / Response Sequences}
\begin{itemize}[leftmargin=*]
    \item \textbf{Stimulus:} Admin opens master complaint table and selects an unassigned ticket.
    \item \textbf{Response:} System opens routing modal displaying active staff members and departments.
    \item \textbf{Stimulus:} Admin assigns staff member and sets priority to \texttt{Critical}.
    \item \textbf{Response:} System updates complaint record, recalculates SLA target time, and writes an audit log.
\end{itemize}

\subsubsection{Functional Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 4.3.A - Master Data Table Filtering:} The system shall provide a master table supporting text search, status/priority/department filtering, sorting, and pagination.
    \item \textbf{Requirement 4.3.B - Staff Ticket Dispatching:} The system shall allow administrators to assign unassigned tickets or reassign active tickets across departments and personnel.
    \item \textbf{Requirement 4.3.C - Priority Override:} The system shall allow administrators to override and elevate or lower the priority level of any complaint.
    \item \textbf{Requirement 4.3.D - User \& Taxonomy Administration:} The system shall provide administrative interfaces to create, edit, or deactivate users and manage category/department lookup tables.
    \item \textbf{Requirement 4.3.E - Immutable Audit Log Viewer:} The system shall display a read-only audit log table recording all system state changes, stamped with actor ID and precise timestamp.
\end{itemize}

\subsection{Resolution Verification \& Student Feedback Subsystem}

\subsubsection{Description and Priority}
This subsystem handles the post-resolution feedback loop, enabling students to verify repairs (closing tickets) or reject repairs (reopening tickets with explanation), accompanied by optional 1--5 star rating feedback. To protect student privacy and encourage honest evaluation without fear of retaliation, the feedback schema supports student anonymity options. Priority: \textbf{Medium}.

\subsubsection{Stimulus / Response Sequences}
\begin{itemize}[leftmargin=*]
    \item \textbf{Stimulus:} Student views a ticket marked \texttt{Resolved}.
    \item \textbf{Response:} System prompts student to click "Confirm Resolution" or "Reject Resolution".
    \item \textbf{Stimulus:} Student clicks "Confirm Resolution" and submits an optional 5-star rating with an anonymity toggle.
    \item \textbf{Response:} System updates ticket status to \texttt{Closed}, records feedback, and archives ticket.
    \item \textbf{Stimulus:} Student clicks "Reject Resolution" and inputs text explanation.
    \item \textbf{Response:} System updates ticket status to \texttt{Reopened}, reverts state to \texttt{In Progress}, and alerts assigned staff.
\end{itemize}

\subsubsection{Functional Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 4.4.A - Resolution Confirmation:} The system shall transition ticket status to \texttt{Closed} upon student confirmation click.
    \item \textbf{Requirement 4.4.B - Resolution Rejection Loop:} The system shall transition ticket status to \texttt{Reopened} and notify staff if a student rejects a resolution action.
    \item \textbf{Requirement 4.4.C - Anonymous Star Rating \& Comments:} The system shall collect optional 1 to 5 star ratings and written feedback comments upon ticket closure, supporting anonymous submission flags to prevent staff retaliation.
\end{itemize}

\section{Other Nonfunctional Requirements}

\subsection{Performance Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 5.1.A - Initial Page Load Speed:} The web application shall render initial dashboard views within 1.5 seconds on standard broadband connections.
    \item \textbf{Requirement 5.1.B - Master Query Latency:} Database queries fetching master complaint records shall execute in under 500 milliseconds for datasets up to 10,000 records.
\end{itemize}

\subsection{Safety Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 5.2.A - Data Loss Prevention:} Database writes shall execute within atomic transactions to prevent partial record insertion.
    \item \textbf{Requirement 5.2.B - System Backup:} Automated daily PostgreSQL database snapshots shall be maintained.
\end{itemize}

\subsection{Security Requirements}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 5.3.A - HttpOnly Cookie Session Security:} Session tokens shall be stored exclusively in \texttt{HttpOnly}, \texttt{SameSite=Lax}, \texttt{Secure} cookies.
    \item \textbf{Requirement 5.3.B - Row Level Security Coverage:} PostgreSQL Row Level Security (RLS) policies shall be enabled on 100\% of database tables.
    \item \textbf{Requirement 5.3.C - Server-Side Input Validation:} All Server Actions and API payloads shall be validated against server-side Zod schemas.
    \item \textbf{Requirement 5.3.D - Storage Mime-Type Filtering:} Attachment uploads shall strictly permit JPEG, PNG, and WEBP file formats, rejecting executable extensions.
\end{itemize}

\subsection{Software Quality Attributes}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 5.4.A - Mobile Usability:} All student and staff interfaces shall be fully responsive down to 320px screen width.
    \item \textbf{Requirement 5.4.B - Reliability \& Constraint Integrity:} Relational foreign key constraints shall prevent orphaned records upon taxonomy or user updates.
    \item \textbf{Requirement 5.4.C - Maintainability:} TypeScript strict mode shall be enforced across all client and server codebase modules.
\end{itemize}

\subsection{Business \& Operational Rules}
\begin{itemize}[leftmargin=*]
    \item \textbf{Requirement 5.5.A - SLA Resolution Targets:} Low priority (7 days), Medium (3 days), High (24 hours), Critical (4 hours).
    \item \textbf{Requirement 5.5.B - Auto-Closure Timeout:} Tickets remaining in \texttt{Resolved} state for 7 consecutive days without student response shall auto-transition to \texttt{Closed}.
\end{itemize}

\subsection{PostgreSQL Relational Table Definitions}

\subsubsection{Table 1: \texttt{users} (Profiles)}
\textit{Operational Note:} \texttt{department\_id} is intentionally left \texttt{NULL} for non-staff roles (\texttt{student} and \texttt{admin}), as only operational \texttt{staff} members belong to specific maintenance departments.

CREATE TYPE user_role AS ENUM ('student', 'staff', 'admin');

CREATE TABLE users (

    role user_role NOT NULL DEFAULT 'student',
    department_id UUID REFERENCES departments(id) ON DELETE SET NULL, -- Intentionally NULL for Students & Admins
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
\end{lstlisting}

\begin{lstlisting}[language=SQL]
CREATE TABLE departments (

    description TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

\subsubsection{Table 3: \texttt{categories}}

CREATE TABLE categories (

    category_id UUID NOT NULL REFERENCES categories(id) ON DELETE RESTRICT,
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    location TEXT NOT NULL,
    priority priority_level NOT NULL DEFAULT 'medium',
    status ticket_status NOT NULL DEFAULT 'submitted',
    sla_due_at TIMESTAMPTZ NOT NULL,
    resolved_at TIMESTAMPTZ,
    closed_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()

\end{lstlisting}

\subsubsection{Table 5: \texttt{progress\_notes}}
\begin{lstlisting}[language=SQL]
CREATE TABLE progress_notes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    author_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    note_text TEXT NOT NULL,
    is_internal BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
\end{lstlisting}

\subsubsection{Table 6: \texttt{attachments}}
\textit{Capacity Note:} \texttt{file\_size\_bytes} is defined as \texttt{INTEGER} (max 2.14 GB), which safely accommodates the 5MB upload ceiling. For future video attachment scaling, \texttt{BIGINT} can be adopted.
\begin{lstlisting}[language=SQL]
CREATE TYPE attachment_type AS ENUM ('initial_evidence', 'repair_proof');

CREATE TABLE attachments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    complaint_id UUID NOT NULL REFERENCES complaints(id) ON DELETE CASCADE,
    uploader_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    file_url TEXT NOT NULL,
    file_type TEXT NOT NULL,
    file_size_bytes INTEGER NOT NULL, -- Integer max (2.14GB) safely covers 5MB ceiling
    attachment_type attachment_type NOT NULL DEFAULT 'initial_evidence',
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
\end{lstlisting}

\subsubsection{Table 7: \texttt{feedback}}
\textit{Privacy \& Anonymity Note:} \texttt{student\_id} is nullable and accompanied by \texttt{is\_anonymous} flag to permit anonymous ratings, preventing staff retaliation.
\begin{lstlisting}[language=SQL]
CREATE TABLE feedback (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    complaint_id UUID UNIQUE NOT NULL REFERENCES complaints(id) ON DELETE CASCADE,
    student_id UUID REFERENCES users(id) ON DELETE SET NULL, -- Nullable for Anonymity
    is_anonymous BOOLEAN NOT NULL DEFAULT FALSE,
    rating INTEGER NOT NULL CHECK (rating >= 1 AND rating <= 5),
    comments TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
\end{lstlisting}

\subsubsection{Table 8: \texttt{audit\_logs} (Immutable Ledger)}
\begin{lstlisting}[language=SQL]
CREATE TABLE audit_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    complaint_id UUID REFERENCES complaints(id) ON DELETE SET NULL,
    actor_id UUID REFERENCES users(id) ON DELETE SET NULL, -- Handles NULL for System Background Tasks
    action TEXT NOT NULL,
    old_state JSONB,
    new_state JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
\end{lstlisting}

\subsection{Database Triggers \& Row Level Security (RLS) Access Policies}

\subsubsection{Complaint Number Generator Trigger}
\begin{lstlisting}[language=SQL]
CREATE OR REPLACE FUNCTION generate_ticket_number()
RETURNS TRIGGER AS $$
DECLARE
    seq_val INT;
BEGIN
    SELECT COUNT(*) + 1 INTO seq_val FROM complaints;
    NEW.ticket_number := 'CMP-' || TO_CHAR(NOW(), 'YYYY') || '-' || LPAD(seq_val::TEXT, 4, '0');
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_ticket_number
BEFORE INSERT ON complaints
FOR EACH ROW EXECUTE FUNCTION generate_ticket_number();
\end{lstlisting}

\subsubsection{Automated Audit Log Trigger (With System Task Fallback)}
\textit{Vulnerability Fix:} Uses \texttt{COALESCE(auth.uid(), actor\_id)} to fall back gracefully to system actor context during automated background actions (e.g., 7-day auto-closure via service role key).
\begin{lstlisting}[language=SQL]
CREATE OR REPLACE FUNCTION log_complaint_audit()
RETURNS TRIGGER AS $$
DECLARE
    executing_actor UUID;
BEGIN
    -- Fallback to system actor context if auth.uid() is NULL (background service actions)
    executing_actor := COALESCE(auth.uid(), NEW.assigned_staff_id, NEW.reporter_id);

    INSERT INTO audit_logs(complaint_id, actor_id, action, old_state, new_state)
    VALUES (
        NEW.id,
        executing_actor,
        TG_OP,
        CASE WHEN TG_OP = 'UPDATE' THEN to_jsonb(OLD) ELSE NULL END,
        to_jsonb(NEW)
    );
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_complaint_audit
AFTER INSERT OR UPDATE ON complaints
FOR EACH ROW EXECUTE FUNCTION log_complaint_audit();
\end{lstlisting}

\subsubsection{Row Level Security (RLS) Sample Policy}
\begin{lstlisting}[language=SQL]
ALTER TABLE complaints ENABLE ROW LEVEL SECURITY;

-- Students view only their own complaints
CREATE POLICY student_select_policy ON complaints
FOR SELECT TO authenticated
USING (auth.uid() = reporter_id OR auth.jwt()->'user_metadata'->>'role' = 'admin');
\end{lstlisting}

\section{User Interface Wireframe Specifications}

\subsection{Student Portal Layout Specification}
The Student Portal layout comprises a top navigation bar (Logo, Notifications, User Profile Menu), a KPI Metric Summary bar (Total Complaints, Pending Actions, Resolved Count), and a main split grid:
\begin{itemize}[leftmargin=*]
    \item \textbf{Left Pane (Submission \& History):} Contains the primary "Lodge Complaint" CTA button and a list of historical complaints with color-coded priority badges.
    \item \textbf{Right Pane (Interactive Timeline):} Displays the selected ticket detail header, physical location details, photo evidence carousel, staff progress notes feed, and the resolution verification banner.
\end{itemize}

\subsection{Staff Resolver Workspace Layout Specification}
The Staff Resolver workspace prioritizes rapid task triage and mobile operation:
\begin{itemize}[leftmargin=*]
    \item \textbf{Header Bar:} Displays active staff member name, assigned department badge (e.g., \textit{IT Infrastructure}), and pending queue counter.
    \item \textbf{Queue Card Grid:} Renders ticket cards sorted by urgency and SLA countdown. Cards display Complaint ID, Priority Badge (\texttt{Critical} highlighted in red), Location, and "Accept Ticket" / "Mark Resolved" quick action buttons.
\end{itemize}

\subsection{Admin Command Center Layout Specification}
The Admin Command Center presents an enterprise data control panel:
\begin{itemize}[leftmargin=*]
    \item \textbf{Metrics Bar:} System-wide KPI indicators (Active Complaints, SLA Compliance Rate, Overdue Count, Avg Resolution Time).
    \item \textbf{Master Data Table:} Full-width data table featuring global text search, column sorting, pagination, and filter dropdowns (Status, Priority, Department, Category).
    \item \textbf{Dispatcher Drawer Modal:} Slide-over panel for manual staff routing, priority override sliders, and database audit log inspection.
\end{itemize}
